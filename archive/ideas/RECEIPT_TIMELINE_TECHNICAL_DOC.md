# ReceiptTimeline — Technical Architecture Document

> **Component**: `ReceiptTimeline.tsx`
> **Path**: `frontend/src/components/zkdefi/ReceiptTimeline.tsx`
> **Version**: Session 15 (March 2026)
> **Dependencies**: `useReceiptAggregator`, `ExplorerLink`, `lucide-react`

---

## 1. Purpose and Architectural Role

The `ReceiptTimeline` is a read-only, chronologically-ordered presentation component that renders the **reconciled view** of all proof receipts generated by the zkDeFi protocol. It occupies a critical position in the system's transparency layer: it is the primary UI surface where users observe the lifecycle of every cryptographic proof and on-chain attestation produced by their identity-bound agents, deposits, withdrawals, rebalances, and ZK-verified executions.

The component does not own any data-fetching logic. It receives a fully reconciled `AggregatedReceipt[]` array from its parent (typically via the `useReceiptAggregator` hook) and renders it as a scrollable timeline with status badges, on-chain explorer links, fact hashes, capital source labels, and human-readable timestamps.

Its architectural significance derives from its position at the convergence point of **two independent data sources**: the backend event store (`orchestration_receipts.json` via `ReceiptService`) and the on-chain receipt indexer (`/api/v1/zkdefi/receipts/on-chain/{address}`). The component itself is stateless — all reconciliation intelligence lives upstream.

## 2. Data Flow Pipeline

The full data pipeline from proof generation to rendered timeline entry spans four layers:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         LAYER 1: PROOF GENERATION                       │
│                                                                         │
│  Circuit Execution → Groth16 Proof → ReceiptService.create_receipt()    │
│  (snarkjs)            (pi_a, pi_b, pi_c)   ↓                           │
│                                      orchestration_receipts.json        │
│                                             ↓                           │
│                                     ReceiptService.confirm_receipt()    │
│                                      (tx_hash written on-chain)         │
└─────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────┐
│                       LAYER 2: BACKEND API                              │
│                                                                         │
│  GET /api/v1/zkdefi/history/timeline/{address}                          │
│                                                                         │
│  Returns: TimelineResponse {                                            │
│    user_address: string;                                                │
│    events: HistoryTimelineEvent[];                                      │
│    count: number;                                                       │
│  }                                                                      │
│                                                                         │
│  Route handler: backend/app/api/routes/state.py::history_timeline()     │
│  Source: ReceiptService.get_user_receipts(address) → dict[] → mapped    │
│  to HistoryTimelineEvent with status normalization                      │
└─────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────┐
│                     LAYER 3: RECONCILIATION                             │
│                                                                         │
│  useReceiptAggregator(address, invalidateKey?)                          │
│     │                                                                   │
│     ├── fetchBackend()  → getHistoryTimeline(address)                   │
│     │      → HistoryTimelineEvent[]                                     │
│     │                                                                   │
│     ├── fetchOnChain()  → apiFetch("/receipts/on-chain/{address}")      │
│     │      → OnChainReceiptEntry[]                                      │
│     │                                                                   │
│     └── useMemo reconciliation:                                         │
│            1. Index backend events by tx_hash                           │
│            2. Index on-chain receipts by tx_hash                        │
│            3. Merge into Map<key, {backend?, chain?}>                   │
│            4. Derive ReceiptReconciliationStatus per entry              │
│            5. Sort newest-first                                         │
│            → AggregatedReceipt[]                                        │
└─────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────┐
│                     LAYER 4: PRESENTATION                               │
│                                                                         │
│  <ReceiptTimeline                                                       │
│    receipts={receipts}                                                  │
│    loading={loading}                                                    │
│    error={error}                                                        │
│    onRefresh={refresh}                                                  │
│  />                                                                     │
│                                                                         │
│  Renders: scrollable <ul> of receipt entries with:                       │
│    - Timestamp (localized)                                              │
│    - Action label (capitalized)                                         │
│    - Proof type badge                                                   │
│    - Asset tag (from meta)                                              │
│    - Capital source label (from meta)                                   │
│    - ReceiptStatusBadge (confirmed/pending/on-chain/diverged)           │
│    - ExplorerLink (Starkscan deep-link to tx)                           │
│    - Fact hash (truncated, with title tooltip)                          │
│    - Result summary (right-aligned)                                     │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. Type Definitions

### 3.1. `AggregatedReceipt` (canonical receipt type)

Defined in `frontend/src/hooks/useReceiptAggregator.ts`:

| Field | Type | Description |
|-------|------|-------------|
| `id` | `string` | Stable identifier: `tx_hash`, backend event id, or synthesized key |
| `proof_type` | `string` | Label: `"groth16"`, `"deposit"`, `"withdraw"`, `"rebalance"`, etc. |
| `action` | `string` | Human-readable action name (e.g., `"deposit"`, `"yield_optimization"`) |
| `timestamp` | `string` | ISO 8601 timestamp of first observation |
| `status` | `ReceiptReconciliationStatus` | One of: `confirmed`, `pending`, `on-chain`, `diverged` |
| `backendEntry?` | `HistoryTimelineEvent` | Raw backend timeline entry (if present) |
| `onChainHash?` | `string` | Transaction hash for block explorer linking |
| `chainId?` | `string` | Chain identifier for explorer URL routing (Sepolia vs mainnet) |
| `factHash?` | `string` | On-chain fact hash registered with the Starknet fact registry |
| `result?` | `string` | Human-friendly result summary from either source |
| `meta?` | `Record<string, unknown>` | Merged metadata from backend + on-chain sources |

### 3.2. `ReceiptReconciliationStatus` (state machine)

```
                    ┌───────────────────────────────────────┐
                    │       RECONCILIATION STATUS FSM        │
                    │                                       │
                    │  Backend only ──────► "pending"        │
                    │  Chain only   ──────► "on-chain"       │
                    │  Both + match ──────► "confirmed"      │
                    │  Both + mismatch ──► "diverged"        │
                    │                                       │
                    │  Special case: backend-only with       │
                    │  terminal status ("confirmed"/"info")  │
                    │  is treated as "confirmed" not         │
                    │  "pending" (bookkeeping events).       │
                    └───────────────────────────────────────┘
```

- **`confirmed`**: Both backend and on-chain sources agree on the terminal state, or the backend has a terminal status with no on-chain counterpart expected.
- **`pending`**: Backend has recorded the receipt but it has not yet appeared in on-chain indexing. Indicates a receipt awaiting Starknet L2 block inclusion.
- **`on-chain`**: The on-chain indexer found this receipt but the backend is not aware of it. Can indicate a receipt from external tooling or a backend restart gap.
- **`diverged`**: Both sources report the receipt but their terminal statuses disagree. A critical anomaly requiring investigation.

### 3.3. `HistoryTimelineEvent` (backend source)

Defined in `frontend/src/types/ekubo.ts`:

| Field | Type | Description |
|-------|------|-------------|
| `id` | `string` | Unique event identifier |
| `timestamp` | `string` | ISO timestamp |
| `type` | `string` | Event type (`"deposit"`, `"withdraw"`, `"rebalance"`, etc.) |
| `title` | `string` | Human-readable title |
| `status` | `"pending" \| "confirmed" \| "failed" \| "info"` | Terminal status |
| `tx_hash?` | `string \| null` | Starknet transaction hash |
| `receipt_id?` | `string \| null` | Internal receipt identifier |
| `venue?` | `string \| null` | DEX venue (e.g., `"ekubo"`, `"jediswap"`) |
| `execution_path?` | `string \| null` | Execution trace reference |
| `policy_hash?` | `string \| null` | Compliance policy hash |
| `details?` | `string \| null` | Extended description |
| `meta?` | `Record<string, unknown> \| null` | Arbitrary metadata |

## 4. Component Interface

### 4.1. Props

```typescript
interface ReceiptTimelineProps {
  receipts: AggregatedReceipt[];   // Pre-reconciled receipt array
  loading: boolean;                 // Whether data is being fetched
  error: string | null;             // Error message (if any)
  onRefresh: () => void;            // Callback to re-fetch both sources
}
```

The component is **purely presentational**: it accepts reconciled data and a refresh callback, performing zero async operations internally.

### 4.2. Typical Consumer Pattern

```tsx
function VaultLedgerView({ address }: { address: string }) {
  const { receipts, loading, error, refresh } = useReceiptAggregator(address);
  return (
    <ReceiptTimeline
      receipts={receipts}
      loading={loading}
      error={error}
      onRefresh={refresh}
    />
  );
}
```

## 5. Internal Sub-Components

### 5.1. `ReceiptStatusBadge`

A private (non-exported) sub-component that maps `AggregatedReceipt["status"]` to a colored pill with an icon:

| Status | Icon | Color | Background |
|--------|------|-------|------------|
| `confirmed` | `CheckCircle` | `text-emerald-400` | `bg-emerald-500/10` |
| `pending` | `Clock` | `text-amber-400` | `bg-amber-500/10` |
| `on-chain` | `Shield` | `text-blue-400` | `bg-blue-500/10` |
| `diverged` | `AlertTriangle` | `text-rose-400` | `bg-rose-500/10` |

Falls back to `pending` styling for unknown statuses (defensive).

### 5.2. `capitalSourceLabel(raw: unknown): string | null`

An inline utility function that normalizes the `meta.capital_source` field into a human-readable label:

| Input | Output |
|-------|--------|
| `"wallet_mode"` | `"Wallet mode"` |
| `"private_capital"` | `"Private capital"` |
| `""` / `null` / `undefined` | `null` (suppresses rendering) |
| Any other string | Underscore-to-space conversion |

## 6. Rendering Logic

The component renders in exactly one of four mutually exclusive states:

1. **Loading** (`loading === true`): Centered spinner with emerald border animation
2. **Error** (`error !== null`): Amber text centered error message
3. **Empty** (`receipts.length === 0`): Instructional placeholder text
4. **Populated**: Scrollable `<ul>` with max height of `400px` and `overflow-y: auto`

Each populated list item renders a flex-wrapped row containing (in order):

```
┌──────────────────────────────────────────────────────────────────────┐
│ [Timestamp]  [Action]  [Proof Type]  [Asset?]  [Capital?]           │
│        [StatusBadge]  [ExplorerLink?]  [FactHash?]  [Result?]       │
└──────────────────────────────────────────────────────────────────────┘
```

- **Timestamp**: Formatted via `Date.toLocaleString()` with `month: "short"`, `day: "numeric"`, `hour: "2-digit"`, `minute: "2-digit"`. Renders as `"—"` if missing.
- **Action**: Capitalized via CSS `capitalize` class.
- **Proof Type**: Subdued `text-zinc-500` styling.
- **Asset Tag**: Conditionally rendered from `meta.asset` as a small rounded badge.
- **Capital Source Tag**: Conditionally rendered as a blue-tinted badge from `meta.capital_source`.
- **Status Badge**: Always rendered via `ReceiptStatusBadge`.
- **Explorer Link**: Conditionally rendered when `onChainHash` exists. Uses `ExplorerLink` component which deep-links to Starkscan (Sepolia by default, mainnet when `chainId` is provided). Displays truncated hash: `{first 8 chars}…{last 4 chars}`.
- **Fact Hash**: Conditionally rendered when `factHash` exists. Displays `fact:{first 8 chars}…{last 4 chars}` with a `title` tooltip showing the full hash.
- **Result**: Conditionally rendered right-aligned as the last element.

## 7. Backend Data Source: `ReceiptService`

**File**: `backend/app/services/receipt_service.py`

The `ReceiptService` is a singleton that manages the lifecycle of constraint receipts:

### 7.1. Storage

- **File-backed**: `backend/data/orchestration_receipts.json`
- **In-memory**: Two dictionaries — `_receipts: dict[str, dict]` (receipt_id → receipt) and `_user_receipts: dict[str, list[str]]` (user_address → list of receipt_ids)
- **Persistence**: Every mutation calls `_persist()` which serializes both dicts to JSON

### 7.2. Receipt Lifecycle

```
create_receipt(user, constraints_hash, proof_hash, action_type, protocol_id, amount)
    │
    ├── Generates receipt_id = SHA-256(user + constraints_hash + proof_hash + timestamp)
    ├── Stores receipt with on_chain=False
    ├── Indexes under user_address
    └── Persists to file
    │
    ↓
confirm_receipt(receipt_id, tx_hash)
    │
    ├── Sets on_chain=True
    ├── Sets tx_hash
    ├── Sets confirmed_at timestamp
    └── Persists to file
```

### 7.3. API Route

**Endpoint**: `GET /api/v1/zkdefi/history/timeline/{user_address}`

**Handler**: `backend/app/api/routes/state.py::history_timeline()`

Fetches all receipts for a user from `ReceiptService.get_user_receipts()`, then maps each raw receipt dict into a `TimelineEvent` with:
- Status normalization (`pending` / `confirmed` / `failed` / `info`)
- Title derivation from action type
- Metadata extraction (venue, tx_hash, etc.)

## 8. Reconciliation Algorithm (`useReceiptAggregator`)

**File**: `frontend/src/hooks/useReceiptAggregator.ts`

The hook performs a **dual-source fetch + merge + reconcile** in three phases:

### Phase 1: Parallel Fetch
```typescript
await Promise.all([fetchBackend(), fetchOnChain()]);
```
Both fetches are **non-fatal**: if either source fails, the other's data still renders. The on-chain indexer endpoint uses a 5-second timeout with zero retries (endpoint may not be deployed).

### Phase 2: Hash-Key Indexing
```typescript
const byHash = new Map<string, { backend?: HistoryTimelineEvent; chain?: OnChainReceiptEntry }>();
```
Both sources are indexed into a shared `Map` keyed by `tx_hash` (or a synthesized fallback key). This enables O(n) merging regardless of source sizes.

Backend events with `type === "local_commitment_migration"` are filtered out (internal bookkeeping).

### Phase 3: Status Derivation
For each merged entry, the reconciliation status is computed:

```
IF backend AND chain:
    normalize both statuses
    IF statuses match OR one is "info" and other is "confirmed":
        → "confirmed"
    ELSE:
        → "diverged"
ELSE IF backend only:
    IF backend.status == "pending":
        → "pending"
    ELSE:
        → "confirmed"  (terminal bookkeeping event)
ELSE (chain only):
    → "on-chain"
```

The result array is sorted **newest-first** by timestamp.

## 9. `ExplorerLink` Component

**File**: `frontend/src/components/zkdefi/ExplorerLink.tsx`

A routing-aware hyperlink that generates Starkscan deep-links for Starknet transactions and contracts.

| Prop | Type | Description |
|------|------|-------------|
| `txHash?` | `string` | Transaction hash (for `type="tx"`) |
| `contractAddress?` | `string` | Contract address (for `type="contract"`) |
| `chainId?` | `string \| null` | Chain selector: omit for Sepolia default |
| `type` | `"tx" \| "contract"` | Link target type |
| `children?` | `ReactNode` | Custom link content |
| `className?` | `string` | CSS class override |

URL generation dispatches to:
- `starkscanTxUrl(txHash, chainId)` for non-Sepolia chains
- `sepoliaStarkscanTxUrl(txHash)` for Sepolia (default)
- `sepoliaStarkscanContractUrl(contractAddress)` for contract links

All links open in a new tab with `rel="noopener noreferrer"`.

The component uses the zkDeFi glass-morphism design system:

- **Container**: `glass rounded-xl border border-zinc-800 p-6` — frosted glass panel with zinc border

- **Badge tokens**: Small rounded pills with 10% opacity backgrounds for asset tags, capital source labels, and status indicators
- **Icons**: Lucide React icon set at `w-5 h-5` (header) and `w-3 h-3` (inline)

## 11. Error Handling and Resilience

The component and its data pipeline implement **progressive degradation**:

| Failure Mode | Behavior |
|---|---|
| Backend API unreachable | `useReceiptAggregator.fetchBackend()` catches silently; on-chain source may still populate |
| On-chain indexer absent | `fetchOnChain()` catches silently with 5s timeout; backend source populates timeline |
| Both sources fail | `error` state rendered with amber text message |
| Malformed receipt data | `capitalSourceLabel()` handles null/undefined; timestamp falls back to `"—"` |
| Unknown status string | `ReceiptStatusBadge` falls back to `pending` styling |
| Missing `onChainHash` | `ExplorerLink` returns `null` (conditional rendering) |
| Missing `factHash` | Fact hash element conditionally skipped |

## 13. Performance Characteristics

- **Render complexity**: O(n) where n = number of receipts. No nested iterations.
- **Scroll virtualization**: Not implemented (max-height with CSS overflow). For >500 receipts, a virtualized list (e.g., `react-virtuoso`) would be advisable.
- **Re-render triggers**: Only when `receipts`, `loading`, or `error` props change. The `onRefresh` callback is stable (from `useCallback` upstream).
- **Network calls**: Zero. All fetching is delegated to the parent hook. The component is a pure presentation layer.
- **Memory**: Each `AggregatedReceipt` is approximately 200–500 bytes. A timeline of 1,000 receipts consumes ~500KB of React state.

## 14. Security Considerations

- **No user input**: The component renders only data from API responses. No `dangerouslySetInnerHTML` or unescaped interpolation.
- **Explorer links**: Use `target="_blank"` with `rel="noopener noreferrer"` to prevent tab-nab attacks.
- **Hash display**: Sensitive hashes (fact hashes, tx hashes) are truncated in display but available via `title` tooltip — no clipboard-copy UX that could leak to monitoring software.
- **Capital source**: The `meta.capital_source` field is sanitized through `capitalSourceLabel()` before rendering, preventing injection of arbitrary DOM content.
